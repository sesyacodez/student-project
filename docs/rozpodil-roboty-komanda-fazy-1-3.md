# Розподіл роботи: три учасники, фази 1–3

Документ узгоджує [student-project-spec.md](./student-project-spec.md), ваш початковий поділ команди та **фактичний стан репозиторію** (моделі, URL, [api-endpoints.md](./api-endpoints.md)). Оновлюйте цей файл, коли змінюється структура або префікси API.

**Поточний спринт (чеклист дій):** [sprint-faza1-zalyshky-faza2.md](./sprint-faza1-zalyshky-faza2.md)

## 1. Поточна структура проєкту (як у коді)

### 1.1. Django-застосунки

У `edumanage/settings.py` підключено: `users`, `branches`, `students_and_groups`, `scheduling`.

| Апка | Моделі (файл) | Примітка |
|------|----------------|----------|
| `users` | `User` | `AUTH_USER_MODEL`, логін за `phone`, ролі ADMIN / TEACHER |
| `branches` | `Branch`, `Subject` | Предмет **прив’язаний до філії**, унікальність `(branch, name)` у БД |
| `students_and_groups` | `Student`, `Group`, `GroupMembership`, `SubscriptionPlan`, `PricingTier`, `StudentSubscription` | Тарифи та призначення планів тут; M2M план ↔ предмет через `branches.Subject` |
| `scheduling` | `LessonTemplate`, `Lesson`, `Attendance` | FK на `users.User`, `branches.Subject`, `Student`, `Group` |

**Важливо для команди:** модель **Subject** фізично в **`branches`**, не в `students_and_groups`. У `scheduling` посилання на предмет має бути `branches.Subject` (узгоджено з кодом після виправлення зв’язків).

### 1.2. База даних і міграції

- У `settings.py` зараз **SQLite** (`db.sqlite3`) — відповідає допустимому старту Фази 1 у спеки.
- Міграції є для: `users`, `branches`, `students_and_groups`.
- Для **`scheduling`** на момент узгодження документа каталог `migrations/` може бути порожнім або відсутнім: після стабілізації моделей потрібно згенерувати **`python manage.py makemigrations scheduling`** і застосувати міграції.

### 1.3. URL і реалізація API

- Файл `edumanage/urls.py` зараз підключає лише **`admin/`**. Публічних REST-маршрутів **ще немає**.
- Канонічний план ендпоінтів — **[api-endpoints.md](./api-endpoints.md)**:
  - база: **`/api/v1/`**;
  - приклад повного шляху: `POST /api/v1/auth/login/` (у документі секції дані відносно цієї бази).

Під час імплементації Фази 2 варто завести щось на кшталт:

- `path("api/v1/", include("…router…"))`  
і тримати реальні шляхи **1:1** з таблицями в `api-endpoints.md` (або явно зафіксувати відмінності в тому ж файлі).

### 1.4. ER-діаграма

Актуальні посилання на діаграми: [db-diagram.md](./db-diagram.md). Після змін моделей оновлюйте діаграму та перевіряйте відповідність коду.

### 1.5. Звірка «код ↔ api-endpoints.md» (розриви на зараз)

| Тема | У `api-endpoints.md` | У коді моделей зараз |
|------|----------------------|----------------------|
| Маршрути REST | повний перелік під `/api/v1/` | не підключені в `urls.py` |
| JWT, refresh rotation, blacklist | описано (`/auth/…`) | немає в `settings`/залежностях до впровадження |
| Призначення користувача на філію | `POST /users/{id}/branches/`, `DELETE …` | у `User` **немає** M2M/FK на `Branch` — треба додати проміжну модель або поле зв’язку |
| Поле «branches» у відповіді логіну | масив id філій | потребує моделі зв’язку User↔Branch + серіалізатор |
| Відвідуваність | один запис на пару урок–студент, upsert | у `Attendance` варто додати **UniqueConstraint**(lesson, student) + `clean`/логіка upsert у Фазі 2 |
| Звітність | `/reports/*` | ендпоінти та агрегації — майбутня робота (Фаза 2–3) |

Ці пункти є **дорожньою картою**, а не критикою: документ API у вас уже добре попрацьований.

## 2. Розподіл відповідальності по апках (щоб не дублювати work)

Через те, що **Subject** у `branches`, логічно так:

- **Учасник 1**: `users` + **`branches`** (у тому числі **Branch** і **Subject** — міграції, адмінка, майбутні DRF-viewsets для філій і предметів *або* явна домовленість передати serializers для Subject Учаснику 2, але файли моделей лишаються в `branches`).
- **Учасник 2**: `students_and_groups` (студенти, групи, тарифи, student subscriptions).
- **Учасник 3**: `scheduling` (шаблони, уроки, конфлікти, відвідуваність) + тісна coordination з моделлю `Subject`/`Branch`.

## 3. Фаза 1 (тижні 1–4) — фундамент

Ціль спеки: моделі, ER, документ API, базова автентифікація, мінімальний UI або views, робочий код.

### Учасник 1 — ядро, філії, предмети (моделі в `branches`), користувачі

- Проєкт, `settings`, `.gitignore`, `AUTH_USER_MODEL`.
- `User`: телефон, ролі, `is_active`; підготовка до JWT (навіть якщо токени — у Фазі 2).
- `Branch` + архівування; заборона «жорсткого» видалення за наявності залежних даних (правила з спеки).
- **`Subject`** у `branches/models.py`: статуси, унікальність у філії (уже є constraint — перевірити бізнес-правила архіву).
- **Зв’язок User ↔ Branch** (потрібно для п. 4.2 і для `api-endpoints.md`): реалізувати модель (наприклад `UserBranchMembership` або M2M через `through`), щоб співпасти з `GET /auth/me/` та списком філій.
- Базові views або адмінка для демонстрації; мінімальний UI за спекою.
- **Deliverable:** підтримувати **[api-endpoints.md](./api-endpoints.md)** у актуальному стані (ви вже маєте сильну базу — доповнювати лише при змінах).

### Учасник 2 — студенти, групи, тарифи (`students_and_groups`)

- `Student`, батьківські поля, `branch`, архівування.
- `Group`, `GroupMembership`, дати входу/виходу, валідація однієї філії (логіка `add_student`/`remove_student` у вас уже закладена).
- `SubscriptionPlan`, `PricingTier`, `StudentSubscription` — відповідає розділам 8–9 у `api-endpoints.md`.
- **Deliverable:** ER-діаграма (оновити [db-diagram.md](./db-diagram.md) або окремий артефакт).

### Учасник 3 — розклад (`scheduling`)

- `LessonTemplate`, `Lesson` (індивідуальний / груповий), статуси.
- **Перевірка конфліктів** (п. 4.7.3): викладач, студент(и), ігнор `cancelled`, суміжні інтервали без зазору не конфлікт.
- `Attendance` — базова модель; узгодити з Учасником 2 список учасників групового уроку.
- **Deliverable:** unit-тести на **overlap**-логіку.
- Після фіксації моделей: **makemigrations** для `scheduling`.

### Спільні deliverables Фази 1

1. ER (зв’язки Branch–Subject–Student–Group–Lesson–…).  
2. Документ API — фактично **`api-endpoints.md`**.  
3. Код: створення користувача, входу (хоча б сесія або заготовка), філії, студента тощо.

### Чеклист «легко пропустити» (Фаза 1)

- [ ] Неактивний користувач не логіниться; однакова відповідь при невірому телефоні/паролі (п. 4.1).  
- [ ] Прив’язка адміна до філій + фільтрація списків.  
- [ ] Мінімальний фронт (Templates/SPA) за п. 5.  
- [ ] Змістовні коміти (п. 6).

## 4. Фаза 2 (тижні 5–8) — DRF, JWT, бізнес-правила, Swagger

Ціль: повний REST під **`/api/v1/`**, JWT (access + refresh, rotation за спекою), права ADMIN/TEACHER, валідація й конфлікти, Swagger, фронт на API.

### Учасник 1

- Підключити DRF, роутер, префікс **`api/v1/`** у `urls.py`.
- SimpleJWT (або аналог): login, refresh, blacklist для logout — як у [api-endpoints.md](./api-endpoints.md) секція 2.
- Viewsets/serializers для **auth**, **branches**, **users** (staff), призначення на філії.
- **Permissions / queryset filtering** за доступними філіями; TEACHER не отримує адмінські колекції.
- **drf-spectacular** (або інший) — глобальна OpenAPI-схема, security scheme JWT.
- API-тести: логін, refresh, 403 на чужі філії.

### Учасник 2

- DRF для **subjects** (моделі в `branches` — імпорт серіалізаторів із відповідного модуля, домовитись про пакет `api` або `branches/serializers.py`).
- CRUD **students**, **groups**, membership-ендпоінти як у секції 7 `api-endpoints.md`.
- **subscription-plans**, **pricing-tiers**, **student-subscriptions** — відповідність тіла запитів прикладам у документі.
- Pagination (згідно приміток у кінці `api-endpoints.md`).
- API-тести: унікальність предмета, заборона student з іншої філії в групі, призначення плану без «чужого» subject.

### Учасник 3

- **lessons**, **lesson-templates**, **conflicts/check**, **preview-conflicts** — секції 10–11.
- **attendance** — секція 12; перевірки cancelled / не-учасник / upsert.
- Інтеграція перевірки конфліктів у `POST/PATCH` уроків.
- Обмеження TEACHER: лише свої уроки в list/detail та у відвідуваності.
- Тести: груповий урок (усі члени групи), cancelled ignored, суміжні слоти.

### Спільно (Фаза 2)

- Розділ **13. Reports** — можна розподілити: Учасник 3 (дані уроків/відвідуваності), Учасник 2 (студенти/філії для статистики), Учасник 1 (обмеження `teacher_id` для TEACHER).
- Формат помилок **14** — узгоджений exception handler у DRF.
- Фронт: усі екрани через API (п. 5–6 спеки).

## 5. Фаза 3 (тижні 9–12) — DevOps, якість, демонстрація

Ціль спеки: Docker Compose (Django + PostgreSQL), оптимізація запитів, тести й гранічні кейси, README, полірування фронту, фінальне демо.

### Учасник 1 — інфраструктура та безпека конфігурації

- **Docker Compose**: сервіси `web` (Django) + `db` (PostgreSQL), томи, мережа; команда старту з кореня проєкту (`docker compose up`).
- Перемикання `DATABASES` через **змінні середовища**; `.env.example` з усіма потрібними ключами (SECRET_KEY, DB, JWT).
- **README.md**: як підняти проєкт, міграції, superuser, тести, змінні оточення (п. 6 спеки).
- Перевірка CORS (якщо SPA окремим origin), `ALLOWED_HOSTS` для контейнера.
- За бажанням (бонус спеки): скелет CI (GitHub Actions — запуск тестів).

### Учасник 2 — продуктивність списків і даних «клієнтів»

- Індекси БД: часті фільтри (`Student.branch_id`, `Group.branch_id`, поля пошуку за ім’ям — за профілем запитів).
- `select_related` / `prefetch_related` у queryset’ах list API для студентів, груп, планів, підписок.
- Пагінація + обмеження N+1 на **GET /students/**, **/groups/**, **/subscription-plans/**.
- Доробка **branch-stats** та інших агрегацій (якщо лишили хвости з Фази 2) з ефективними запитами (`Count`, `Avg` тощо).
- Розширення тестів на граничні кейси CRUD (архіви, restore).

### Учасник 3 — розклад, тести, надійність

- Оптимізація **conflict check**: один запит на діапазон дат / викладача / студентів; індекси за `(date, teacher_id)` тощо.
- Повне покриття спеки п. 6: **user model**, **lesson + conflicts**, **attendance**; додаткові integration-тести API.
- Обробка edge cases з п. 4.7–4.8 (шаблони з частковими конфліктами — за обраною політикою).
- Полірування сценаріїв демо: створення шаблону → генерація → відміна → відвідуваність → звіт.

### Спільні deliverables Фази 3

- Один репозиторій збирається та запускається **однією командою** Compose.  
- Звіт по тестах (локально / CI).  
- Фінальна презентація: сценарії з критеріїв оцінювання (п. 8 спеки).  

### Бонуси (п. 9 спеки) — за силами, поза обов’язковим мінімумом

Експорт CSV, dashboard по ролях, CI/CD — розподіл за інтересом після закриття мінімуму Фази 3.
